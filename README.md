# HelpFlow

Веб-застосунок для обробки звернень служби підтримки (helpdesk). Клієнти подають звернення через власний портал, система автоматично розподіляє їх між агентами за навантаженням, контролює терміни SLA та ескалує прострочені звернення.

## Основні можливості

- реєстрація та автентифікація (JWT) з ролями client / agent / admin;
- клієнтський портал: створення звернень, перегляд статусу власних звернень;
- автоматичне призначення звернення агенту з найменшим поточним навантаженням;
- розподіл звернень за категоріями, призначеними операторам;
- автоматичний розрахунок дедлайну SLA за категорією та ескалація прострочених звернень;
- Kanban-дошка з drag-and-drop зміною статусу, фільтрами та мобільним перемикачем статусів;
- публічні коментарі, внутрішні нотатки та вкладення у зверненнях і повідомленнях;
- кілька операторів-учасників одного звернення;
- повторне звернення, пов’язане із закритим або вирішеним;
- керування категоріями та користувачами (адміністратор).

## Системні вимоги

- Python 3.11+
- Node.js 18+
- PostgreSQL 14+ (опційно для локальної розробки — достатньо SQLite)

## Встановлення backend

```bash
cd backend
python -m venv .venv
source .venv/bin/activate      # Linux/macOS
.venv\Scripts\activate         # Windows

pip install -r requirements.txt
copy .env.example .env
```

Налаштування бази даних (міграції):

```bash
flask --app run:app db upgrade
```

## Встановлення frontend

```bash
cd frontend
npm install
copy .env.example .env
```

## Змінні середовища

**backend/.env**

| Змінна | Опис | Приклад |
|---|---|---|
| `DATABASE_URL` | рядок підключення до БД | `postgresql://user:password@localhost:5432/helpflow` (або `sqlite:///helpflow.db` для локальної розробки) |
| `JWT_SECRET_KEY` | секретний ключ для підпису JWT | випадковий довгий рядок |
| `CORS_ORIGINS` | дозволені адреси frontend через кому | `http://localhost:5173` |
| `FLASK_ENV` | середовище виконання | `development` / `production` |
| `ALLOW_DEMO_ROLE_REGISTRATION` | дозволяє тестову реєстрацію агентів та адміністраторів | `false` |

**frontend/.env**

| Змінна | Опис | Приклад |
|---|---|---|
| `VITE_API_BASE_URL` | адреса backend-API | `http://localhost:5000/api` |

## Опис API

Основні групи API:

| Група | Базовий шлях | Призначення |
|---|---|---|
| Auth | `/api/auth` | реєстрація, вхід |
| Tickets | `/api/tickets` | створення та керування зверненнями |
| Comments | `/api/tickets/<id>/comments` | публічні коментарі та внутрішні нотатки |
| Categories | `/api/categories` | категорії звернень та їх SLA |
| Users | `/api/users` | керування користувачами (адміністратор) |

Перший обліковий запис адміністратора створюється локально:

```bash
flask --app run:app create-admin admin@example.com
```

Команда запитає пароль без відображення у терміналі.

## Підготовка до розгортання

Backend потребує Python-хостинг із PostgreSQL, наприклад Render або Railway. У production необхідно задати `DATABASE_URL`, `JWT_SECRET_KEY`, `CORS_ORIGINS` і `FLASK_ENV=production`; після цього виконати `flask --app run:app db upgrade` та створити першого адміністратора через `flask --app run:app create-admin admin@example.com`. Production-команда запуску backend: `gunicorn run:app` з робочою директорією `backend`.

Для тестового демо можна додати `ALLOW_DEMO_ROLE_REGISTRATION=true`. Тоді вкладка «Оператор → Реєстрація» дозволяє створювати агентів і адміністраторів. У реальному середовищі змінна має бути `false`.

Frontend підготовлений для Vercel: файл `frontend/vercel.json` зберігає маршрути React SPA під час прямого відкриття сторінки. Перед збіркою його змінна `VITE_API_BASE_URL` має містити повну адресу backend, наприклад `https://api.example.com/api`. Після появи адреси frontend її потрібно додати до `CORS_ORIGINS` backend. Файли вкладень у поточній реалізації зберігаються на диску backend, тому для постійного production-сховища потрібно підключити S3-сумісне сховище до початку використання з реальними даними.

## Приклад типового сценарію

1. Клієнт реєструється та подає звернення через `POST /api/auth/register` → `POST /api/tickets`.
2. Система обирає агента з мінімальним навантаженням серед операторів, закріплених за категорією, і обчислює `sla_deadline`.
3. Агент бачить звернення на Kanban-дошці, бере його в роботу (`PATCH /api/tickets/<id>`, статус `in_progress`).
4. Агент та клієнт обмінюються коментарями (`POST /api/tickets/<id>/comments`); агент додатково залишає внутрішню нотатку, недоступну клієнту.
5. Агент позначає звернення вирішеним; якщо дедлайн SLA порушено раніше — система вже підвищила пріоритет автоматично.
