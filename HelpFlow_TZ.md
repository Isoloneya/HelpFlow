# Технічне завдання проєкту HelpFlow

**Дисципліна:** Сучасні технології веб-розробки
**Тип роботи:** Індивідуальне семестрове завдання
**Технологічний стек:** Python (Flask), React, SQLAlchemy, PostgreSQL/SQLite, JWT

---

## AC-01. Опис та постановка задачі

### Назва проєкту

HelpFlow

### Предметна область

Веб-застосунок для обробки звернень служби підтримки (helpdesk) — реєстрація, розподіл, супровід та контроль термінів виконання тікетів.

### Проблема

Невеликі команди підтримки не мають доступного інструменту для прозорого розподілу звернень між агентами та контролю дотримання термінів реагування (SLA). Звернення губляться в неструктурованих каналах (пошта, месенджери), навантаження між агентами розподіляється нерівномірно, а порушення термінів виявляється лише постфактум.

### Цільова аудиторія

- невеликі команди технічної або клієнтської підтримки (2–10 агентів);
- клієнти або внутрішні співробітники організації, які подають звернення та очікують на їх вирішення.

### Призначення системи

Система дозволяє клієнтам подавати звернення через власний портал і відстежувати їх статус; дозволяє агентам та адміністраторам отримувати автоматично розподілені звернення, супроводжувати їх до вирішення та контролювати дотримання термінів SLA.

### Основні сценарії використання

1. Клієнт реєструється/логіниться в клієнтському порталі.
2. Клієнт створює нове звернення, обираючи категорію та описуючи проблему.
3. Система автоматично призначає звернення агенту з найменшим поточним навантаженням і обчислює дедлайн відповідно до SLA категорії.
4. Агент бачить призначені йому звернення на робочій дошці (за статусами: нове → в роботі → вирішено → закрито).
5. Агент або клієнт додають коментарі до звернення; агент додатково може залишати внутрішні нотатки, недоступні клієнту.
6. Агент змінює статус звернення в міру опрацювання.
7. Система позначає звернення, що наближаються до порушення SLA або вже прострочені, та підвищує їм пріоритет (ескалація).
8. Адміністратор керує користувачами, категоріями та переглядає всі звернення незалежно від призначення.

### Перелік ключових функцій

- реєстрація та автентифікація (JWT) з рольовою моделлю (client / agent / admin);
- створення та перегляд звернень із обмеженням видимості для клієнта (лише власні звернення);
- автоматичне призначення агента за поточним навантаженням;
- розрахунок і контроль дедлайну SLA, автоматична ескалація прострочених звернень;
- публічні та внутрішні коментарі з розмежуванням доступу за роллю;
- Kanban-дошка звернень для агентів/адміністраторів із фільтрацією за статусом, пріоритетом, агентом;
- керування категоріями звернень (адміністратор);
- обробка помилкових сценаріїв (спроба доступу до чужого звернення, спроба клієнта отримати внутрішню нотатку тощо).

## AC-02. Архітектура та структура системи

### Загальний підхід

Клієнт-серверна архітектура з повним розділенням frontend і backend, що взаємодіють виключно через REST API. На відміну від серверно-рендереного підходу, тут frontend — самостійний React SPA (Single Page Application), що звертається до Flask-бекенду через `fetch`/`axios`.

### Компоненти системи

**Client (React SPA).** Побудований на Vite. Відповідає за весь UI: клієнтський портал і робочу панель агента/адміністратора в межах одного застосунку з маршрутизацією (React Router) та розмежуванням доступних сторінок за роллю користувача.

**Backend (Flask).** Організований через **Blueprints** — кожна предметна область (auth, tickets, comments, categories, users) є окремим Blueprint з власним набором маршрутів. Усередині кожного Blueprint зберігається той самий поділ на шари, що й у попередньому проєкті:

| Шар | Відповідальність |
|---|---|
| Route (view-функція) | приймання HTTP-запиту, валідація вхідних даних, виклик сервісу, формування відповіді |
| Service | бізнес-логіка: автопризначення агента, розрахунок SLA, перевірка прав на коментарі |
| Repository / Model-запити | доступ до даних через SQLAlchemy |

**Database.** PostgreSQL для production, SQLite для локальної розробки та тестування — підтримка обох без зміни коду за рахунок SQLAlchemy.

### Обґрунтування архітектурних рішень

- Flask обраний замість Django через мінімалізм: проєкту не потрібна вбудована адмінка чи ORM, нав'язана фреймворком — Flask дозволяє зібрати архітектуру (Blueprint → Service → Model) свідомо, під конкретні потреби проєкту.
- React SPA, а не серверний рендеринг — виправдано інтерактивністю робочої панелі (Kanban-дошка з перетягуванням, живі фільтри), де SPA-підхід дає кращий UX, ніж перезавантаження сторінки при кожній дії.
- Розділення на Blueprints замість одного `app.py` з усіма маршрутами — застосування Single Responsibility на рівні модуля, полегшує навігацію по коду при зростанні кількості ендпоінтів.

### Наскрізний потік запиту (приклад: створення звернення)

Client (React) → `POST /api/tickets` (JWT у заголовку) → Route-функція Blueprint'а `tickets` валідує тіло запиту → Service перевіряє категорію, обирає агента з мінімальним навантаженням, обчислює `sla_deadline` → Model зберігає звернення в БД → Route серіалізує відповідь у JSON → Client оновлює список тікетів.

## AC-03. Користувацький інтерфейс

### Клієнтський портал

| Маршрут (React Router) | Призначення |
|---|---|
| `/login`, `/register` | вхід та реєстрація |
| `/my-tickets` | список власних звернень клієнта зі статусами |
| `/my-tickets/new` | форма створення нового звернення |
| `/my-tickets/:id` | деталі звернення: опис, статус, публічна переписка |

### Робоча панель агента/адміністратора

| Маршрут | Призначення |
|---|---|
| `/dashboard` | Kanban-дошка звернень (колонки за статусами) з фільтрами за пріоритетом, агентом, категорією |
| `/tickets/:id` | деталі звернення: повна переписка (публічна + внутрішня для агента), зміна статусу/пріоритету/призначення |
| `/categories` | керування категоріями та їх SLA-параметрами (адміністратор) |
| `/agents` | керування користувачами-агентами (адміністратор) |

### Навігація

Верхня панель адаптується до ролі: клієнт бачить пункти "Мої звернення" та профіль; агент/адміністратор — "Дошка", "Категорії" (лише admin), "Агенти" (лише admin) та профіль.

### Форми введення

| Форма | Поля |
|---|---|
| Реєстрація | email, пароль, підтвердження пароля |
| Логін | email, пароль |
| Нове звернення | тема, опис, категорія |
| Коментар | текст, позначка "внутрішня нотатка" (лише для агента/адміністратора) |
| Категорія | назва, термін SLA (у годинах) |

Кожна форма проходить клієнтську валідацію з негайним відображенням помилки та повторну валідацію на сервері.

### Відображення даних

Kanban-дошка відображає звернення карточками, згрупованими за статусом, з індикацією пріоритету кольором та позначкою прострочення SLA. Деталі звернення показують хронологічну стрічку коментарів; внутрішні нотатки візуально відрізняються від публічних (позначка "Внутрішньо"), клієнту такі коментарі взагалі не передаються в API-відповіді.

### Повідомлення користувачу

Успішні дії супроводжуються короткочасним спливаючим повідомленням. Помилки валідації відображаються інлайново під полем; помилки бізнес-логіки — банером з описом, зрозумілим користувачу, без технічних деталей.

### Адаптивність

Інтерфейс адаптується під desktop та mobile: Kanban-дошка на мобільних пристроях перетворюється на список із перемиканням між статусами замість паралельних колонок; форми відображаються в одну колонку.

## AC-04. Робота з даними

### Перелік сутностей

| Сутність | Опис | Основні поля |
|---|---|---|
| User | обліковий запис | id, email, password_hash, role (client/agent/admin), created_at |
| Category | категорія звернень | id, name, sla_hours |
| Ticket | звернення | id, title, description, status, priority, category_id, client_id, assignee_id, sla_deadline, created_at |
| Comment | коментар до звернення | id, ticket_id, author_id, body, is_internal, created_at |

### Обмеження цілісності даних

- `email` унікальний та обов'язковий;
- `Ticket.status` — значення з переліку `new`, `in_progress`, `resolved`, `closed`;
- `Ticket.priority` — значення з переліку `low`, `medium`, `high`, `urgent`;
- `Comment.is_internal = true` дозволено створювати лише користувачам з роллю `agent` або `admin`;
- видалення `Category` забороняється, якщо існують звернення цієї категорії (або реалізується через архівацію, аналогічно категоріям у попередньому проєкті);
- `Ticket.assignee_id` завжди посилається на користувача з роллю `agent` або `admin`.

### Операції над сутностями

| Сутність | Створення | Читання | Оновлення | Видалення |
|---|---|---|---|---|
| Ticket | клієнт (власне звернення) | клієнт — власні; агент/адмін — призначені або всі | агент/адмін (статус, пріоритет, призначення) | не передбачено (звернення закривається, а не видаляється) |
| Comment | автор звернення або будь-який агент/адмін | учасники звернення (внутрішні — лише агент/адмін) | не передбачено | не передбачено |
| Category | адміністратор | усі автентифіковані користувачі | адміністратор | адміністратор (за відсутності активних звернень) |
| User | реєстрація (client); адміністратор створює агентів | власний профіль; адміністратор — усіх | власний профіль; адміністратор — ролі інших | адміністратор |

## AC-05. Форми та валідація

### Рівні валідації

1. **Клієнтська валідація (React)** — попередня перевірка вводу в браузері (обов'язковість полів, формат email, довжина тексту) для миттєвого фідбеку.
2. **Валідація на рівні схеми (Flask, наприклад через Marshmallow або Pydantic)** — структурна перевірка вхідного JSON.
3. **Валідація на рівні бізнес-логіки (Service)** — правила, що залежать від стану системи: доступність агента, приналежність категорії, права на створення внутрішньої нотатки.

### Правила валідації за формами

| Поле | Правило | Рівень |
|---|---|---|
| email (реєстрація) | коректний формат, унікальність | клієнт + схема + сервіс |
| password | мінімум 8 символів | клієнт + схема |
| Ticket.title | 1–150 символів, обов'язкове | клієнт + схема |
| Ticket.description | обов'язкове, до 5000 символів | клієнт + схема |
| Ticket.category_id | категорія має існувати | сервіс |
| Comment.body | обов'язкове, до 2000 символів | клієнт + схема |
| Comment.is_internal | дозволено лише для ролі agent/admin | сервіс |
| Category.sla_hours | додатне ціле число | схема |

## AC-06. Взаємодія frontend і backend

### Механізм взаємодії

React-застосунок звертається до Flask-API виключно через REST з передачею даних у форматі JSON. У розробці React (Vite dev-server) і Flask працюють на різних портах, тому backend налаштовує `flask-cors` для дозволеного походження (origin) фронтенду; у production обидва розгортаються так, щоб уникнути CORS (наприклад, збірка React віддається тим самим доменом через reverse proxy, або залишається CORS з фіксованим дозволеним origin).

### Автентифікація на рівні транспорту

Після успішного логіну клієнт отримує JWT (через `Flask-JWT-Extended` або аналог), який передається в заголовку `Authorization: Bearer <token>` при кожному наступному запиті. Формування заголовків централізоване в єдиному API-клієнті на фронтенді.

### Структура API

```
Auth:        POST /api/auth/register
             POST /api/auth/login

Tickets:     POST   /api/tickets
             GET    /api/tickets            (з фільтрами: status, priority, assignee_id)
             GET    /api/tickets/<id>
             PATCH  /api/tickets/<id>       (статус, пріоритет, призначення)

Comments:    POST /api/tickets/<id>/comments
             GET  /api/tickets/<id>/comments

Categories:  POST   /api/categories
             GET    /api/categories
             PATCH  /api/categories/<id>
             DELETE /api/categories/<id>

Users:       GET   /api/users               (адміністратор)
             PATCH /api/users/<id>          (зміна ролі, адміністратор)
```

### Формат обробки помилок

Усі помилки повертаються в єдиному форматі:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "У вас немає доступу до цього звернення"
  }
}
```

| Код HTTP | Умова виникнення |
|---|---|
| 400 | порушення бізнес-правила |
| 401 | відсутня або недійсна автентифікація |
| 403 | недостатньо прав доступу |
| 404 | ресурс не знайдено |
| 409 | конфлікт даних |
| 422 | помилка валідації вхідних даних |

│   ├── components/

### Застосування принципів SOLID та DRY

- Кожен Blueprint відповідає за одну предметну область (Single Responsibility).
- Логіка автопризначення агента та розрахунку SLA винесена в `ticket_service.py` — єдине місце, що використовується і при створенні звернення, і за потреби при повторному перепризначенні.
- Перевірка ролі користувача реалізована через переиспользуваний декоратор (наприклад, `@role_required("agent", "admin")`), що уникає дублювання перевірок у кожному маршруті.
- На фронтенді єдиний API-клієнт централізує додавання JWT-заголовка та обробку помилок, уникаючи дублювання `fetch`-викликів у кожному компоненті.

## AC-10. Залежності та конфігурація

### Backend

| Бібліотека | Призначення |
|---|---|
| Flask | веб-фреймворк |
| Flask-SQLAlchemy | ORM |
| Flask-Migrate | міграції БД (обгортка над Alembic) |

## AC-13. Обробка помилок

Обробка реалізована через глобальні обробники помилок Flask (`@app.errorhandler`), що перетворюють кастомні винятки бізнес-логіки на єдиний формат відповіді. Помилки валідації схем автоматично перетворюються на 422 з переліком некоректних полів. Непередбачені винятки перехоплюються загальним обробником: клієнту повертається загальне повідомлення без деталей, повний стек — у серверний лог.

## AC-14. Розгортання

Backend розгортається на платформі з підтримкою Python (Render, Railway або аналог) з PostgreSQL як базою даних production-середовища. Frontend збирається (`vite build`) і розгортається окремо як статичний сайт (Vercel, Netlify) або віддається тим самим сервером через reverse proxy — обидва варіанти обґрунтовуються складністю проєкту та зручністю CORS-налаштування. Змінні середовища задаються через налаштування хостингу, а не файл.
